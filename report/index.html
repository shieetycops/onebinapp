Jembatan Rilis

Tombol "Download" yang memberi installer yang benar untuk Windows, macOS, atau Linux, dibangun di atas GitHub Releases. Situs tidak menyimpan file.

Keputusan Tahan dulu: perbaiki classifier, uji ulang, baru pilot.

Cakupannya mendukung idenya: 73,7% repo punya installer siap klik untuk Windows atau macOS, dan pilihan classifier cocok dengan manifest winget di 90,2% kasus Windows x64 (macOS vs Cask: 81,6%). Angka strict itu memasukkan tebakan arsitektur; dengan arsitektur tertulis di nama, mac x64 turun ke 41,7% dan Linux arm64 ke 24,3%. Tetapi syarat yang saya tetapkan sendiri, classifier OS ≥ 95%, tidak lolos pada angka paling ketat.

  • Angka paling ketat untuk OS adalah recall macOS 85,7% (18 dari 21), dan seluruh 21 baris macOS acuannya hanya kesepakatan dua pelabel, tanpa satu pun berdasar isi file (DMG, zip, dan tar tidak terbaca dari awal file). Akurasi OS 91,0% bila baris tidak terselesaikan dihitung salah (n=100), 94,8% bila dikeluarkan (n=96), dan 96,8% hanya pada baris yang acuannya isi file (n=31, satu salah). Sebabnya ada di classifier dan bisa diperbaiki (lihat langkah 3), tetapi 100 asset ini sudah terlihat, jadi perbaikannya harus diuji pada sampel baru. terukur
  • Pembanding dan sampel bersih (lihat langkah 3, lanjutan): aturan Komi Store tidak lebih baik untuk tugas ini, classifier gabungan v2 naik ke OS 99,0% pada 100 baris dev tetapi hanya 91,7% pada 400 asset baru (sama dengan v1), dan gerbang OS tidak lolos pada ketiga classifier. Angka terendah yang dikunci adalah precision macOS strict 79,4%, artefak dari label "ragu" per baris; yang mengikat sebenarnya recall macOS 84,7% dan Linux 83,2%. Sebagian besar kesalahan datang dari binary CLI tanpa ekstensi yang tidak akan ditawarkan produk ini, jadi sampel tersebut belum menguji installer aplikasi desktop secara bersih. terukur
  • Sudah ada pesaing dengan tujuan mirip: Komi Store, dulu bernama GitHub Store dikutip. Ia berupa aplikasi yang harus dipasang dulu. Bahwa jalur "klik di browser, tanpa aplikasi" masih kosong dan dicari orang awam adalah asumsi, dan inilah yang diuji pada 5 pengguna.
  • Hanya 33,3% repo punya installer strict untuk ketiga OS. Produknya tidak bisa menjanjikan "selalu ada" untuk Linux.

Syarat lanjut: setelah classifier diperbaiki, semua angka OS (akurasi strict, akurasi tanpa baris tidak terselesaikan, akurasi isi-file saja, dan precision serta recall tiap kelas Windows, macOS, Linux) ≥ 95% pada sampel yang bersih dan lebih besar. Sampel bersih berarti asset dari repo yang belum pernah diambil, bukan undian baru dari asset yang dipakai menulis aturan. Sampel 400 asset yang sudah dipakai sekarang menjadi data dev. Sampel ketiga (sekitar 1.184 repo belum terlihat) perlu aturan cakupan dan kepercayaan pelabel per kolom yang ditetapkan sebelum penarikan. Ukurannya sekitar 60 baris acuan atau lebih per OS, karena dengan 21 baris satu kesalahan saja sudah menentukan lolos atau gagal. Lalu minimal 4 dari 5 pengguna awam berhasil memasang satu app tanpa bantuan.

Langkah 3

Classifier nama asset

Classifier memetakan nama asset ke (OS, arsitektur, tipe). Aturannya ada di scripts/classifier.py, ditulis dari asset di luar sampel evaluasi, dan tidak diubah selama evaluasi. Pemilih (picker) dipisah dan diuji di langkah 4. Evaluasi seluruhnya dikerjakan agent, tanpa label manusia.

Gerbang OS ≥ 95% tidak lolos pada angka paling ketat

Angka paling ketat adalah yang terendah dari semua ukuran OS di bawah: recall macOS 85,7% (18 dari 21), seluruhnya berdasar kesepakatan dua pelabel dan bukan isi file. Dua kegagalan akan menurunkannya ke 81%, satu kegagalan lebih sedikit menaikkannya ke 90%, jadi gerbang ini ditentukan oleh beberapa baris. Sampel: 100 asset dari 77 repo (seed tetap, maksimal 2 per repo).

Cara evaluasi

  • Isi file. Request Range ke awal tiap asset (512 KB). Terbaca untuk 31 dari 100: PE 11, ELF (AppImage) 6, .deb 12, .rpm 2. Tidak terbaca dari awal file: .dmg, zip, tar.gz, tar.xz, apk, snap, dan file teks (checksum, yml, json, sig). Bukti mentah ada di data/evidence/.
  • Aturan PE 32-bit. Header PE 32-bit tidak menunjukkan arsitektur target installer, karena penyetel NSIS dan WiX berupa program 32-bit. Ke-11 baris PE bermesin x86; 9 membawa penanda installer. Maka untuk PE, OS Windows tetap dipakai, tetapi arsitektur dari header hanya dipercaya jika 64-bit. Aturan ini ditetapkan dari bukti sebelum angka apa pun dihitung. Tanpa aturan ini, installer arm64 dan x64 akan terbaca x86 dan classifier dihukum untuk kesalahan pengukuran.
  • Dua pelabel buta. labeler-a (opus) dan labeler-b (sonnet), hanya tools Read, hanya menerima nama asset dan panduan label. Mereka sepakat di 99 dari 100 baris untuk OS, 100 untuk arch, dan 99 untuk tipe. Dua model yang membaca panduan sama berbagi konvensi, jadi kesepakatan ini bukan konfirmasi independen.
  • Putaran resmi. Putaran pertama memakai tipe agent pengganti karena labeler-a dan labeler-b belum terdaftar di sesi. Hasilnya diarsipkan di data/labeler_*_run1.csv dan tidak dipakai. Putaran resmi dipilih sebelum perbandingan apa pun dihitung.
  • Label acuan. OS dan arch: isi file bila terbaca; selain itu label yang disepakati kedua pelabel, kecuali keduanya ragu atau berbeda, yang ditandai "tidak terselesaikan" dan dihitung salah untuk classifier. Tipe: hanya kesepakatan kedua pelabel, karena isi file tidak menentukan tipe.

Classifier gabungan (v2) keputusan pada tingkat aturan

  • Diambil dari Komi: pencocokan token per batas kata (dipakai juga untuk kata kunci OS), alias yang hilang (armeabi, armeabi-v7a, v7a, armel, i586, noarch), dan urutan universal, x64, arm64, x86, arm.
  • Tidak diambil: nama tanpa token dianggap universal, override darwin/universal, dan OS dari ekstensi saja.
  • Dipertahankan dari kita: kelas portable, penyaring bukan-installer. Diperbaiki: debug hanya sebagai kata utuh, dbgsym ditolak, .app.tar.gz dikenali macOS, arsip tanpa kata OS tetapi bertoken arsitektur atau "portable" dihitung portable.
  • File: scripts/classifier_v2.py. classifier.py tidak diubah. Hash sha256 ketiga file dikunci di data/classifier_hashes.txt sebelum sampel bersih ditarik.

Gerbang OS ≥ 95% tidak lolos untuk ketiganya

Angka terendah yang sudah ditetapkan sebelumnya adalah precision macOS pada hitungan strict: 0,794 untuk v2 (50 benar dari 63 jawaban macOS). Angka ini artefak pengukuran: 13 dari 63 baris itu berlabel "tidak terselesaikan", dan 12 di antaranya adalah .dmg yang kedua pelabel beri macOS, tetapi keduanya menandai baris "ragu" (soal arsitektur, yang memang kosong). Saya menerapkan "ragu" per baris pada ketiga kolom, jadi label OS yang jelas ikut tidak terselesaikan. Pada baris terselesaikan precision macOS v2 adalah 1,000. Angka ini tetap saya laporkan karena itu definisi gerbang yang saya kunci sebelum melihat data.

Angka yang benar-benar mengikat: recall macOS v2 0,847 (50 dari 59), recall Linux 0,832, recall Windows 0,951, dan akurasi OS 91,7% pada baris terselesaikan. Dua yang pertama gagal dengan sendirinya. macOS punya 59 baris acuan, satu di bawah target sekitar 60.

Apakah keuntungan v2 di data dev pindah ke sampel bersih?

  • OS: tidak. v1 dan v2 sama-sama 330 benar dari 360. Dua selisihnya saling meniadakan: v2 benar pada ChatGPT-MJ_universal.app.tar.gz (perbaikan .app.tar.gz), tetapi v2 salah pada copilot-linuxmusl-arm64.tar.gz yang dulu benar di v1. Batas kata membuat linux tidak lagi cocok di dalam "linuxmusl", jadi ini regresi buatan v2. Ada satu bug lagi yang sejenis dengan debug/"debugger": source di daftar tolak masih cocok sebagai potongan kata, sehingga sourcegit_2026.24.win-x64.zip ditolak.
  • arch: sedikit. v2 benar di 7 sel yang v1 salah, dan salah di 1 sel yang v1 benar. Pada baris isi file keduanya 69,5%.
  • tipe: 99,4% vs 98,8% pada baris terselesaikan, selisih 2 baris.
  • Jadi kenaikan 0,95 di dev lebih banyak berasal dari aturan yang dibentuk oleh baris dev itu sendiri daripada dari perbaikan umum.

Mengapa sampel bersih gagal: pergeseran populasi, bukan hanya classifier

  • 27 dari 30 kesalahan OS v2 adalah file tanpa installer klasik: binary CLI tanpa ekstensi (officecli-linux-x64, kortix-darwin-arm64, ttyd.aarch64), .dll, .ko, .com. Acuannya isi file (ELF, Mach-O, PE), OS-nya jelas, tetapi classifier menandainya bukan installer lalu mengosongkan OS. Produk ini tidak akan menawarkan file seperti itu kepada orang awam.
  • Penyebabnya aturan penarikan yang kami tetapkan: sampel bersih tidak melalui kurasi "apakah ini aplikasi desktop" seperti 300 repo awal. Itu pilihan yang dikunci sebelum penarikan, jadi gerbang tidak saya ubah setelah melihat hasil.
  • Dua hal ini harus dibaca bersama: hasil yang dikunci gagal, dan sampel ini tidak menunjukkan classifier gagal pada installer aplikasi desktop. Yang pertama menentukan keputusan, yang kedua menentukan apa yang perlu diuji berikutnya.
  • Komi lebih baik pada satu hal: arch pada baris isi file 89,0% vs 69,5%. Itu karena ia membaca token arsitektur dari binary tanpa ekstensi, sedangkan v1 dan v2 mengosongkan arch lewat penyaring bukan-installer. Ini pola "Komi benar, kita salah" yang sungguhan, dan sebabnya sama dengan kegagalan OS di atas.

Sampel ini sekarang menjadi data dev. Saya sudah memeriksa baris-barisnya satu per satu. Setiap v3 butuh sampel ketiga (sekitar 1.184 repo masih belum terlihat). Sebelum menarik, tetapkan dua hal: aturan cakupan (kurasi nama dan deskripsi, atau kelas tipe untuk binary telanjang) dan kepercayaan pelabel per kolom, bukan per baris.

Angka sisa kuota dari /rate_limit juga tidak konsisten dengan header respons pada percobaan berotentikasi. Saya memakai header respons sebagai bukti. Ulangi percobaan dari jaringan rumah sebelum membangun.

A. API dari browser pengguna

Biaya server nol. Kesegaran sampai 60 detik. Tiap kunjungan memakai kuota alamat IP pengguna: 60 per jam tanpa token, dibagi seluruh jaringan yang sama (kantor, kampus, warnet). Satu halaman app butuh 1 panggilan, lebih jika /latest tidak cukup (19 dari 51 kasus tanpa installer). Picker harus berjalan di browser. Kalau kuota habis, tombol mati tanpa cadangan.

B. Katalog statis terjadwal

Satu pekerjaan terjadwal membawa token dan menulis satu file JSON. 300 repo = 300 panggilan per jam (6% dari 5.000), dan 304 gratis dengan token, jadi ribuan repo muat. Katalog 300 app berukuran 57 KB terukur; untuk 10.000 app sekitar 1,9 MB ekstrapolasi. Kesegaran sama dengan jeda jadwal (misalnya 1 jam). GitHub Pages: situs maks. 1 GB, batas lunak 100 GB per bulan dan 10 build per jam (tidak berlaku bila dibangun dengan workflow Actions sendiri). Pages tidak boleh dipakai sebagai hosting gratis untuk bisnis daring atau layanan komersial, jadi untuk produk komersial pakai hosting statis lain. dikutip docs.github.com

C. Edge cache

Satu fungsi edge memegang token, memanggil GitHub sesuai permintaan, dan menyimpan hasilnya selama 60 detik. Kesegaran paling baik, kuota tidak bergantung pada IP pengguna. Ada kode yang dijalankan dan token yang dijaga. Contoh tarif (Cloudflare Workers): paket gratis 100.000 permintaan per hari dan 10 ms CPU per pemanggilan, paket berbayar minimal US$5 per bulan, permintaan ke aset statis gratis dan tanpa batas. dikutip developers.cloudflare.com. Penyedia lain tidak diperiksa.

Rekomendasi: B sebagai dasar. Tombol mengarah langsung ke URL rilis GitHub (file tidak lewat situs). Tambahkan A hanya sebagai penyegar opsional untuk satu app yang sedang dibuka, dengan If-None-Match. Pindah ke C hanya jika jeda jadwal terbukti terlalu lambat.

Langkah 6

Dua cara "update" tanpa menyimpan data pengguna

1. Daftar app di browser sendiri

Daftar "app saya" disimpan di localStorage perangkat pengguna. Saat halaman dibuka, ia membandingkan versi yang tercatat dengan katalog dan menandai yang lebih baru.

Dikorbankan: tidak ada notifikasi, hanya terlihat saat halaman dibuka. Tidak sinkron antar perangkat. Hilang kalau data browser dihapus. Situs tidak tahu versi yang benar-benar terpasang, hanya yang diklik.

2. Feed per app

Setiap app punya tautan ke releases.atom GitHub, yang bisa dibaca pembaca RSS atau diteruskan ke email oleh layanan pihak pengguna. Tidak butuh akun di situs ini.

Dikorbankan: orang awam jarang punya pembaca RSS. Feed tidak membedakan OS atau arsitektur, dan hanya memberi kabar, bukan pembaruan. Pengguna tetap mengunduh ulang.

Tidak ada yang melakukan pembaruan otomatis di komputer pengguna. Itu butuh aplikasi terpasang, dan itulah jalur Komi Store, UniGetUI, dan sejenisnya.

Lapisan kepercayaan

Yang terukur dari data

  • 91,5% asset (3.237 dari 3.538) membawa field digest sha256 dari GitHub, jadi verifikasi hash bisa otomatis. terukur
  • Attestation: dari 33 repo sampel yang punya digest, 4 (12%) punya attestation provenance. Sisanya menjawab 404. Sampelnya kecil. terukur

Kriteria kurasi yang diusulkan

  • Masuk katalog hanya jika: ≥ 1.000 bintang, rilis dalam 12 bulan, asset diunggah oleh pemilik repo, bukan fork, ada digest, dan ada installer strict untuk minimal satu OS. asumsi

  • Pemindaian: cari hash asset di layanan reputasi (misalnya VirusTotal) saat katalog dibangun. Kuota dan syarat layanan belum diperiksa.

Langkah 8

Kebijakan merek GitHub dan pesaing

Merek dikutip dari brand.github.com/foundations/logo

  • Memakai merek dagang dan logo GitHub butuh izin tertulis. Dilarang menyiratkan GitHub adalah pembuat atau pendukung produk Anda.
  • Logo GitHub tidak boleh dijadikan logo produk, domain, atau akun sosial, dan tidak boleh diubah warna atau digabung dengan kata lain.
  • Halaman itu tidak punya aturan terpisah untuk nama produk yang memuat kata "GitHub". Pesaing yang memakai kata itu, kemudian berganti nama menjadi Komi Store, menunjukkan risikonya. Alasan penggantian nama itu tidak diperiksa. Pakai nama netral dan tulis "tidak berafiliasi dengan GitHub".
